1. Le passage strict à la Signature V4

C'est le coupable n°1. Les anciennes méthodes de signature (V2) sont désormais obsolètes. Si votre fournisseur S3 (comme un vieux Minio ou une région AWS spécifique) attend de la V2 ou si votre configuration ne précise pas explicitement la région, la 18.8 peut échouer là où la 18.5 "passait" par tolérance.

Solution : Forcez la signature V4 dans votre gitlab.rb :
gitlab_rails['lfs_object_store_connection'] = {
  'provider' => 'AWS',
  'region' => 'votre-region', # Indispensable pour la V4
  'aws_signature_version' => 4,
  # ...
}

Si vous utilisez un proxy ou un Object Storage compatible S3 (Scaleway, DigitalOcean, Minio), Workhorse exige désormais que les paramètres endpoint et path_style soient parfaitement alignés entre les blocs lfs et artifacts.

Si vous avez ceci, vérifiez bien :

    'path_style' => true : Obligatoire pour Minio ou si votre URL est de type [s3.example.com/bucket](https://s3.example.com/bucket).

    'path_style' => false (par défaut) : Pour AWS ou les URL type bucket.s3.example.com.
    
Comment vérifier si c'est un problème de signature ?

sudo tail -f /var/log/gitlab/gitlab-workhorse/current

Pourquoi l'upgrade en 18.11.2 est quand même recommandé ?

Il y a eu des correctifs dans la 18.10 concernant justement la manière dont Workhorse gère les requêtes pré-signées vers S3. Si vous êtes victime d'un bug de "handshake" introduit dans la 18.8, la 18.11.2 est beaucoup plus stable sur ce point.

Vérifiez ce point précis : Dans votre /etc/gitlab/gitlab.rb, avez-vous bien une region de définie ? Même pour un Minio local, il faut souvent mettre us-east-1 par défaut pour que la Signature V4 fonctionne.
